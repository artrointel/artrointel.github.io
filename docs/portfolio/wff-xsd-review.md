## 다음 공동 리뷰의 초점

### 2026-11-14 — 회고 1의 정의·재사용 모델 구체화

- 사용자 제공 설계 의도: scene graph의 계층·선언 순서를 XML에 대응하고, 요소·속성·타입을 분리해 가능한 한 원자적인 정의를 재사용한다. 렌더링/비렌더링 요소, 범용 시각 요소·시계 바늘·Complication, 정적 구성·런타임 동작을 설명의 중심으로 구성했다.
- 회고 1은 ‘워치페이스 XML을 XSD로 어떻게 정의할 것인가’에서 출발하도록 다시 작성했다. `draft: true`를 유지하며 사용자가 추가 디테일을 보강할 상태다. 기존 레이아웃 제약과 Part 명명 회고는 말미에 보존했다.
- 공개 버전 1의 `sourceType.xsd`, `colorAttributes.xsd`, `geometricAttributes.xsd`, `dimensionType.xsd`, `Transform`, `Gyro`, `AbstractPartType`, `PartDraw`, `HourHand`, `Group`, `ComplicationSlot`을 GitHub 도구로 확인했다. 렌더링 순서와 XSD의 추상화·타입 파생은 Android 공식 문서와 W3C Primer도 참고했다.
- 정확성 구분: XML 인스턴스의 선언·순회 순서와 XSD 파일의 정의 나열 순서는 다르다. XML의 포함 관계와 XSD 타입 파생도 구분한다. `Group`은 자체 그리기 기능이 없는 렌더링 계층 컨테이너다.
- 내장 타입의 ‘override’는 원래 타입을 바꾸는 것으로 설명하지 않고 `xs:restriction`으로 파생 타입에 제약을 추가하는 것으로 표현했다. `sourceType`의 도메인별 enumeration·union 조합과 ARGB/RGB 패턴을 예로 들었다.
- 속성 설명의 해석: 사용자 문장 중 ‘별도 타입 선언 회피’는 앞뒤의 재사용 원칙과 대조하여 ‘속성마다 익명 타입을 중복 선언하지 않고 공통 이름 있는 타입을 참조하는 방식을 우선’으로 해석했다. 공개 정의에 익명 타입 예외도 존재함을 확인했다. 이후 리뷰에서 사용자 의도와 맞는지 확인할 항목이다.
- 동적 동작 설명은 렌더링 요소의 기본 속성과 하위 Transform/Gyro의 런타임 표현식을 구분하는 것으로 작성했다. XML 속성 전체가 언제나 정적이라는 일반화는 하지 않았다.
- 사용자 추가 설명 전까지 유지할 항목: 원자적 분리의 실제 판단 기준, 타입 재사용 예외, 구체적인 요소 설계 사례. 검증의 한계와 convention 세부 내용은 별도 편에서 보강한다.
- 검증: `npm.cmd run build` 통과. 로컬 회고 1 URL의 HTTP 200·새 제목·타입/속성 본문 반영을 확인했다. Markdown 포맷과 `git diff --check` 확인. 브라우저 시각 검증은 미실행.

### Runtime 채택 범위·문장 교정 반영

- 사용자 추가 설명: Android 플랫폼에 채택·통합된 대상에는 포맷뿐 아니라 WFF를 로드하고 렌더링·기능 실행을 담당하는 Watch Face Runtime도 포함된다. 머리말의 채택 대상을 이 범위로 명확히 했다. Runtime 전체를 사용자의 개인 구현으로 확대하지 않는다.
- 팀 인원·소속을 소개하는 독립 문장 없이 주기적인 팀 내 설계 논의와 XSD 구현 과정으로 서술했다. 기존 인원·기여 사실은 작업 기록에 유지하되 공개 본문에 반복하지 않는다.
- ‘첫 과정’과 ‘정의의 결과’를 자연스럽고 구체적인 표현으로 바꿨다. GWD 이름에 출처 링크를 통합하고, 회고 자료와 코드 참조 기준을 별도 문단으로 나눴다.

### 초기 설계 경험을 공유하는 목적과 배경 흐름 정리

- 시리즈의 중심은 WFF의 명세를 XSD로 설계·구현하던 초기 경험과 공개 코드만으로는 알기 어려운 설계 의도·판단을 공유하는 것이다. XSD 적용의 장단점은 이 경험을 통해 함께 살펴본다.
- 배경을 ‘Tizen에서 Wear OS로’로 정리하고, 내부 위키 명세 개선 문제는 XML/XSD 선택 절로 이동했다.
- DWF는 초기 명칭에서 WFF로 이어졌다는 설명에 한 번만 사용했다. WFS와의 관계를 별도로 설명하거나 이후에도 옛 명칭을 반복하지 않는다.
- 회고 범위를 구글과의 협업 이전으로 제한하던 문장을 제거했다. 새로 제공되지 않은 연혁·개인 기여·검증 결과는 추가하지 않았다.

### DWF 배경과 시리즈 목적 구체화

- 사용자 직접 경험: 내부 초기 명칭은 DWF(Declarative Watch Face)였다. 삼성의 플랫폼 전환에 맞춘 WFS·포맷 개발로 시작했으며, 처음부터 Android 표준화를 목표로 한 프로젝트는 아니었다. 정기적인 구글 미팅에서 소개된 뒤 긍정적인 검토와 개발팀 간 리뷰·회의를 거쳐 채택·통합 및 WFF 명칭으로 이어졌다는 맥락을 머리말에 반영했다.
- 해당 과정의 세부 경위는 사용자 회고에 근거한다. 공개 Git 이력만으로 명칭 변경 시점·내부 의사결정·통합 과정을 입증했다고 설명하지 않는다.
- 시리즈의 목표: WFF 사례를 통해 XML 정의에 XSD를 적용할 때의 장단점을 간접적으로 살펴볼 수 있는 참고 자료. 다른 프로젝트 대비 XSD 활용 규모·희소성은 주장하지 않는다.
- 사용자는 정확한 설계 연도 추적을 우선하지 않기로 했다. 대략적인 기억을 본문에 연도로 확정하거나 정확한 날짜 확인을 선행 과제로 두지 않는다.

### 시리즈 읽는 순서 변경

- 사용자 지정 순서: 머리말 → 요소·타입 설계 → coding convention → Validation.
- 머리말의 후속 글 안내와 세 편의 제목 번호·목차를 일치시켰다. 파일명과 URL은 유지했다.
- 머리말은 현재의 논리적 흐름을 유지한다. 기술 세부 사항은 후속 편에서 다루고, 추가 설명이 필요한 사실은 근거 작성 과정에서 확인한다.

### 머리말 통합 개고

- 사용자 지시: 머리말은 뼈대 수준을 넘어 완성도 높은 원고로 다듬는다. 문장별 보완을 누적하기보다 전체 흐름과 표현을 함께 검토한다.
- WFF의 전체 명칭·Wear OS에서의 역할을 도입에 설명하고, WFS 제작 도구와 WFF 포맷을 구분했다. 내부 포맷에서 공개 WFF로 이어진 세부 일정은 추가하지 않았다.
- 구성: WFF와 설계 문제 소개 → 내부 위키 명세·플랫폼 전환 → XML/XSD 선택 → 팀의 설계·구현 논의 → 협업 기록에 대한 회고·공개 자료 → 주제별 글 안내.
- 검증 대상은 XML 문서의 스키마 적합성으로 명확히 했다. Loader의 구현·동작 자체를 표준 validator가 검증한다는 뉘앙스를 제거했다.
- 담당 비중·동료의 지식 수준·대안 부재를 강조하는 표현과 반복 안내를 줄였다. 세미나의 내용과 기술적 논의를 중심으로 서술했다.
- 머리말의 초안 안내 문구를 본문에서 제거하고 중복되던 목차·설계 문제를 통합했다. `draft: true`와 비색인 설정은 유지한다. 원고 품질 개선과 공개 승인은 별개다.
- 주제별 글의 검증 한계·coding convention 등은 여전히 추가 설명을 바탕으로 보강할 상태다.

### 머리말의 서술 관점·협업 회고 반영

- 사용자 피드백: 담당 범위를 반복 구분하고 구현 비중을 강조하면 자기 공로를 주장하거나 다른 영역에 무관심했던 인상을 줄 수 있다.
- 머리말의 ‘담당 범위’ 절을 팀에서 설계를 구체화하던 과정으로 바꾸고, ‘거의 전부 제가 진행’ 대신 논의를 요소·타입으로 구현해 가는 서술로 수정했다. 작업용 기록의 기여 사실은 유지하되 공개 본문에서 반복 입증하지 않는다.
- XML 기반을 이어간 기술 선택은 머리말로 이동했다. 요소·타입 설계 편은 구조의 구체적인 설명에 집중한다.
- 사용자 추가 회고: 삼성·구글 간 보안 규약과 시스템적 제약으로 동료들의 commit history가 매끄럽게 이어지지 못했다. 이를 협업과 설계 기록의 연속성에 대한 아쉬움으로 머리말에 반영했다. 구체적인 이관 절차나 보안 규칙을 추정하지 않는다.
- 공개 자료의 개인 기여 입증 한계에 관한 반복 문장을 줄였다. 근거 범위에 관한 상세 대조는 이 작업용 기록에서 유지한다.
- 편집 기준: 역할은 구체적인 문제·논의·설계·구현 과정에서 드러내고, 자기 평가나 공로의 양적 강조를 반복하지 않는다. 정확성을 위한 검토와 독자를 향한 서술을 구분한다.

### 시리즈 분리 반영

- 사용자 요청에 따라 기존 글을 배경·담당 범위·시리즈 안내·공개 자료 맥락을 담은 머리말로 줄였다. 기존 URL은 유지한다.
- 첫 배경 문장부터 ‘내부 위키에 텍스트로 작성·관리한 명세’라고 명시했다. Validation 편에도 같은 맥락을 독립적으로 설명했다.
- Validation 편에는 도입 동기·기대 효과·검증 경계의 보강 항목을 옮겼다. 요소·타입 설계 편에는 scene graph·레이아웃 제약·추상 Part·Part 명명 회고를 옮겼다. Coding convention 편에는 배경과 후속 보강 범위를 옮겼다.
- 네 글에 상호 연결된 시리즈 목차를 추가했다. 별도의 시리즈 스키마·UI는 추가하지 않았다.
- Validation 한계와 coding convention의 구체적인 내용은 사용자 추가 설명 후 작성한다. 분리했다고 각 편의 근거 검토가 완료된 것은 아니다.
- 분리 후 검증: 네 개발 URL의 HTTP 200·글 제목·시리즈 링크를 확인했다. 프로덕션 빌드와 변경 Markdown 포맷 검사 통과, 생성 HTML/XML의 시리즈 참조 0건을 확인했다. 브라우저의 시각 검증은 미실행.

본문의 흐름과 사용자 경험의 표현이 맞는지 검토한다. GWD·WFS·DWF·WFF의 관계는 사용자 후속 설명을 반영했으며, 정확한 연도 추적은 우선 과제로 두지 않는다. 검증의 경계는 사용자가 추후 다루자고 했으므로 지금 즉답을 요구하지 않는다.

- 추후 추가할 것: 검증 한계의 구체적 사례, XSD coding convention의 구체적 규칙·근거, 추상 Part의 공통 책임 분리 이유, 내부에서 공개로 전달된 경위를 명시하는 커밋이 있으면 해당 링크. 사용자에게 즉답을 요구하지 않는다.
- 아직 판단하지 않은 것: 기존 Resume의 `Created WFF` 등 문구 유지·수정 여부. 초안 리뷰가 끝나기 전에 기존 페이지 문구를 변경하지 않는다.
- 이번 주장의 정리 결과: 화면비 제약과 공개 이력의 설명 범위를 구체화했다. 새 기술 성과·측정 결과·비교 실험은 추가하지 않았다.

### 용어·논리 흐름 리뷰 반영

- 사용자 피드백: 읽기 쉬운 표현을 우선하면서 렌더링 scene을 ‘화면’ 등으로 단순화하여 기술적 정확성과 전문성이 약해졌다.
- 반영: 렌더링 scene·scene graph·렌더링 노드, XML 요소 트리, 스키마의 타입·구성 제약을 구분해 서술했다. 물리 디스플레이 해상도·화면비, 가상 캔버스·좌표계, 적응형 레이아웃도 구분했다.
- 타입 설계는 `xs:complexType`, `abstract`, `xs:complexContent`, `xs:extension`으로 구체화했다. 이는 앞서 확인한 공개 XSD의 표현이며 새 개인 기여를 추가한 것이 아니다.
- 서술 흐름: 기존 포맷의 명세 문제 → 담당 범위 → 렌더링·동작 모델과 제약 → scene graph의 XML 표현 → 타입 파생 → 명명 규칙 → 검증 경계.
- 편집 기준: 기술 개념을 쉬운 단어로 대체하기보다 정확한 명칭을 쓰고 처음 등장할 때 짧게 설명한다. 확인되지 않은 런타임 구현과 검증 정책은 추가하지 않는다.

## 검증

### 경력 맥락·설계 동기 리뷰 반영

- 기존 XML 명세는 내부 위키에 있었다. 초기 초안의 문서 부재로 읽힐 수 있는 표현을 수정했다.
- 구조적 재설계는 네 명이 함께 주기적으로 논의했고 XSD 구현은 거의 전부 사용자가 수행했다. 역할 설명을 해당 범위로 조정했다.
- ‘PPT 문서화·내부 발표’ 자체를 실적으로 나열하는 문장을 XSD 학습·팀 내 세미나의 목적과 내용으로 교체했다. 문법·철학·한계, 워치페이스 정의 방식과 coding convention 설명 경험을 기록했다.
- 표준 validator 활용과 기대한 개발 품질·장기 검증 비용의 이점을 선택 근거로 추가했다. 실측 개선 수치는 없다.
- Part 명명은 회고 사례로 분리했다. 검증 한계와 XSD coding convention은 사용자 추가 설명 후 보강한다.

- `npm.cmd run build` 통과: 콘텐츠 로딩과 Markdown 처리를 포함해 정적 빌드 완료. PowerShell 실행 정책으로 `npm.ps1` 실행이 막혀 `npm.cmd`를 사용했다.
- 빌드된 HTML/XML 전체에서 `wff-xsd-design-rationale-ko` 참조 0건을 확인했다. draft 글의 공개 경로·목록·피드 노출은 생성되지 않았다.
- 변경한 세 Markdown 파일의 Prettier 검사와 `git diff --check` 통과. 브라우저 미리보기는 수행하지 않았다.
- XSD 자체 또는 개념도를 실행 가능한 워치페이스로 검증하는 작업은 포함하지 않는다. 글의 도식은 개념 설명이다.

### 로컬 미리보기 추가 확인

- 개발 URL의 HTTP 200, 실제 글 제목과 본문 응답을 확인했다. 브라우저 화면의 시각 검증은 미실행.
- 개발 모드 draft 허용 변경 후에도 프로덕션 빌드가 통과했으며, 생성 HTML/XML의 초안 참조 0건을 다시 확인했다.
- 기본 브라우저 자동 열기는 실행 환경의 접근 거부로 실패했다. 사용자가 위 URL로 직접 접속할 수 있도록 안내한다.
