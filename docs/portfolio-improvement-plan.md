## 1. 프로젝트 목적과 성공 기준

단순한 기술·경력 목록을 넘어, 국내 대기업 및 주요 IT 기업의 경력직 채용에서 시니어 소프트웨어 엔지니어로서의 전문성, 실제 기여, 문제 해결 능력과 기술적 깊이를 전달한다.

핵심 전문성은 **Android Graphics, Platform Engineering, 시스템 설계, 성능 최적화**다. 최근 AI 및 End-to-End 제품 개발 경험은 이 전문성의 확장으로 표현한다. 최종 소개 문구, 직함 표기, 목표 직무의 우선순위는 아직 결정하지 않았다.

향후 검토에 사용할 성공 기준 제안:

- 첫 방문자가 짧은 탐색으로 전문 분야와 대표 기여를 설명할 수 있다.
- 채용 담당자는 경력·역할·성과를 빠르게 파악하고, 기술 면접관은 설계 판단과 기술 근거까지 따라갈 수 있다.
- 주요 주장은 본인의 기여 범위 및 확인 가능한 자료와 연결된다.
- 메인, Resume, 사례, About, Lab, Blog가 각자의 역할을 가지며 필요한 맥락을 서로 연결한다.
- 한·영 페이지의 사실관계가 일치하고 모바일에서도 핵심 정보에 접근할 수 있다.

수치형 목표나 성능 기준은 기준선 확인 후 합의한다. 조회수·채용 성과 등 현재 측정하지 않은 결과를 약속하지 않는다.

웹페이지의 목표는 외부 독자가 전문성·기여·역할 범위를 합리적으로 이해하고 **면접에서 더 확인할 가치가 있다고 판단하도록 돕는 것**이다. 모든 경력을 페이지에서 완벽하게 입증하는 것을 완료 조건으로 삼지 않는다.

## 2. 사용자 요청에서 확정된 작업 원칙

1. 중요한 구조·콘텐츠·디자인 변경은 분석과 논의를 먼저 진행한다.
2. 경력, 성과, 기술적 기여, 정량 수치를 추측하거나 과장하지 않는다.
3. 기존 콘텐츠와 설계 의도를 파악하고 가치 있는 자산을 보존한다.
4. UI, 문구, 기술적 구현, 콘텐츠 구성은 해당 작업 시점에 논의한다.
5. 검토·검증 가능한 작은 단위로 진행한다.
6. 여러 날짜·Codex 세션의 맥락을 저장소 문서로 유지한다.
7. 개선 목적이 명확하지 않은 리팩터링이나 구조 변경은 우선하지 않는다.
8. **근거부터 쌓는 bottom-up 방식으로 진행한다.** 근거 작성은 기존 주장을 방어하는 작업이 아니라 업적·역량을 재점검하는 과정이다. 근거 부족·한계·불확실성이 드러나면 주장도 수정·축소·유보하거나 재정의한다. 최종 포지셔닝과 요약 문구는 이 결과를 바탕으로 정리한다.

현재 허용된 작업은 분석·계획 문서화와 사용자가 요청한 WFF 블로그 초안 작성·공동 리뷰다. 다음 작업을 제안했다는 사실만으로 구현 합의가 성립하지 않는다. 반대로 이미 합의된 범위의 일상적인 세부 작업마다 반복 확인하지 않는다.

## 5. 현 상태의 강점, 문제점과 개선 기회

### A. 메인 페이지와 개인 브랜딩

**강점:** Android Graphics·Platform·AI 제품 경험을 이미 소개하고, 그래픽스·성능·시스템 설계 역량을 구분해 보여준다.

**관찰:** 메인은 Hero → 역량 6개 → 개발 철학 → 최근 글 순서다. 대표 프로젝트의 문제·기여·결과를 직접 요약하는 섹션은 없다. 한·영 Hero의 핵심 경력 설명에 `hidden sm:inline`이 적용되어 작은 화면에서는 해당 설명이 숨겨진다.

**개선 기회:** 핵심 전문 분야의 우선순위, 대표 기여를 보여주는 근거, Resume·사례로 가는 경로를 함께 검토한다. 현재 AI가 핵심 전문성과 병렬로 제시되는 부분이 사용자의 ‘전문성 확장’ 방향과 맞는지도 논의한다. 최종 문구와 레이아웃은 미정이다.

### B. Resume 및 경력 기술

**강점:** GPU 드라이버부터 그래픽스, 창작 플랫폼, 최근 제품 개발까지 연속적인 이력이 있고, 병행 역할 및 학생 프로그램을 별도로 구분한다. WFF 관련 커밋·공식 문서, 특허, 제품 영상 등 근거로 활용할 링크가 존재한다.

**관찰:** 일부 항목은 역할·결과를 명확히 적지만, 병목·제약·설계 대안·검증 조건은 짧거나 생략돼 있다. 영문 WFF 항목의 `Created WFF`와 한글의 ‘XML 스키마를 설계’는 독자가 받아들이는 기여 범위가 다를 수 있다.

**개선 기회:** 팀 성과와 개인 기여, 최초 설계와 개발 참여, PoC와 제품 적용을 구분한다. 기간 중복과 총 경력 산정, 직함 번역, 제품 적용 범위를 확인하고 한·영의 의미를 맞춘다. 정량 자료가 없으면 확인 가능한 정성적 결과로 기술한다.

### C. 대표 프로젝트 및 Engineering Case Study

**강점:** WFF/Watch Face Studio, Wonderland, VanillaVibes, Blur 등 후보가 있고 실제 결과물 자료도 일부 존재한다. Blur 글에는 렌더링 단계·샘플링·compositor 접근을 설명하는 기술 내용이 있다.

**관찰:** Resume 모달은 결과물 확인에 유용하지만 문제 → 제약 → 판단 → 본인 기여 → 검증 → 결과를 하나의 사례로 읽는 구성과는 차이가 있다.

**개선 기회:** 기술 글의 일반 해설과 개인 실무 사례의 역할을 구분하고 상호 연결한다. 별도 페이지, 기존 글 보강, Resume 상세 확장 중 어떤 방식이 적합한지는 사례 1개의 자료를 정리한 후 결정한다.

### D. About 및 경력 서사

**강점:** 수학적 기반과 제품 시스템 개발의 연결, 개발 원칙과 주요 성과가 이미 제시돼 있다.

**관찰:** 메인과 전문 분야·철학 설명이 반복된다. About의 `10+`, `15+`, `5+`, `20+`와 영문 ‘millions of Galaxy users’는 산정 범위·근거 확인이 필요하다. 현재 저장소의 공개 글 개수만으로 ‘기술 글 20+’의 진위를 판단할 수는 없다. 외부 글·발표 등 포함 여부가 미정이다. 외부 스톡 이미지에 본인의 작업 공간처럼 읽힐 수 있는 alt가 있어 의미 적절성도 검토 대상이다.

**개선 기회:** GPU → 렌더링 → 플랫폼 → 제품 개발로 이어지는 서사의 사실을 정리하고, 각 페이지의 설명 역할을 조정한다. 확인 전 수치를 임의로 수정·삭제하지 않는다.

### E. Lab 및 개인 프로젝트

**강점:** 최근 웹 앱과 모드, 그래픽스 실험, Wear OS, 초기 프로젝트가 연도·유형별로 정리되어 있고 결과물 링크가 있다.

**관찰:** 설명은 용도와 기술 태그 중심이다. 본인이 정의한 문제, 설계·검증·운영 판단은 드러나기 어렵다. 영문 `AI-Assisted Toys`와 한글 ‘AI 활용 프로젝트’는 인상의 차이가 있다.

**개선 기회:** 채용에서 의미 있는 소수 프로젝트부터 본인 역할과 기술적 판단을 보강한다. AI 사용은 필요한 만큼 설명하되, AI 사용 여부나 사용 도구 이름을 역량의 근거로 대신하지 않는다. 프로젝트 간 우열·분류 변경은 아직 결정하지 않는다.

### F. Blog 및 기술 콘텐츠

**강점:** Blur·멀티 윈도우·3D 회전 글의 한·영 대응, Mali GPU 번역·해설 3편, 신경망 글 등 전문성을 뒷받침할 자산이 있다. 수식 렌더링과 관련 글 기능도 구성돼 있다.

**관찰:** `src/data/post/`에는 16개 문서가 있고 `src/utils/blog.ts`가 템플릿 글 6개를 제외한다. 나머지는 번역본 포함 10개 문서, 주제 기준 7개이며 발행일은 2017~2020년이다. 영문 Blog는 전체 언어 글을, 한글 Blog는 한국어 글을 조회한다. 영문 메인의 최근 글도 전체 언어를 포함하도록 설정돼 있다.

**개선 기회:** ‘최근’과 ‘대표’ 중 방문 목적에 맞는 노출 방식, 번역본 중복, 원문 번역·해설과 독자 연구의 구분, 기존 경로·RSS·시리즈 링크의 연속성을 검토한다. 오래된 글은 작성 시점과 유효 범위를 표시하는 방안을 논의하며 일괄 재작성하지 않는다. 제외된 템플릿 글이 현재 공개되고 있다고 단정하지 않는다.

### G. UI/UX, 다국어 및 웹사이트 품질

**강점:** 공통 위젯·레이아웃, 테마 전환, 언어 토글, 메타데이터·sitemap·hreflang·이미지 처리 기반이 존재한다.

**확인된 점검 후보:** 핵심 소개의 모바일 숨김, 한·영 본문의 별도 관리, 번역 없는 글의 언어 이동 및 alternate 처리, 과거/현재 URL의 canonical·sitemap·RSS 관계, 영상·임베드의 로딩 및 모달 접근성.

**운영 문서 관찰:** README는 AstroWind 템플릿 설명 중심이며 현 프로젝트의 한·영 구조를 설명하지 않는다. Decap CMS의 글 경로는 `src/content/post`, 실제 loader는 `src/data/post`다. 사용 여부와 영향이 확인된 뒤 필요 시 정리한다.

반응형·접근성·성능·SEO가 나쁘다고 아직 결론 내리지 않는다. 기존 기능 존재가 품질 통과를 뜻하지도 않는다. 전체 리팩터링이나 프레임워크 교체의 근거는 현재 없다.

### 7.1. 사용자 추가 설명 — WFF 및 VanillaVibes

2026-11-13 사용자가 제공한 경력 맥락이다. 아래 경험은 **사용자 직접 설명**을 근거로 기록하며, 공개 자료로 독립 확인한 상태와 구분한다. 외부 입증이 어렵다는 이유만으로 수행 경험을 배제하거나 내부 자료 반출을 요구하지 않는다.

**WFF:** 기존 Tizen 워치페이스 XML 명세는 담당자들이 내부 위키에 텍스트로 문서화하고 있었다. XSD는 없었지만 명세 자체가 없거나 완전한 black box였던 것은 아니다. 사용자는 기존 구조의 분석·재설계와 XSD 설계·구현을 담당했다. 구조적 재설계는 네 명이 주기적으로 논의했고, XSD의 실체 구현은 거의 전부 사용자가 수행했다. 공동 설계와 개인 구현을 구분한다.

팀에 XSD가 익숙하지 않아 사용자가 학습한 문법·철학·정의 방식·한계를 세미나로 공유하고, 워치페이스 요소·구조의 구체적 정의와 coding convention의 방향을 설명했다. PPT는 이러한 기술 공유를 위한 자료였다. 원본은 삼성 내부에 있어 가져올 수 없지만, 설계 근거를 기억에 기반해 재작성할 수 있다.

XSD 선택의 중요한 이유는 표준 validator로 개별 워치페이스 XML을 검증할 수 있다는 점과, 그로부터 기대한 개발 품질·장기 검증 비용의 이점이었다. 측정된 효과로 과장하지 않는다. Validation의 구체적인 한계와 XSD coding convention은 사용자가 추후 설명할 예정이며, Part 명명은 여러 회고 중 하나로 다룬다.

**VanillaVibes(VV):** 사용자는 프레임워크 코어 팀에서 VV를 삼성 내부 라이브러리로 개발했다. AAR 형태로 내부 발행했으며, 다른 삼성 앱 팀과 일부 프레임워크 팀이 import하여 사용했다. 소비 팀은 특정 소수 팀으로 고정된 것이 아니라 개발 방향에 따라 여러 내부 팀으로 확장될 수 있는 구조였다. 소비 팀 수·정확한 목록·채택을 조율한 과정은 아직 구체화하지 않았다.

사용자는 현재도 삼성 인하우스 앱·서비스에서 VV의 렌더링을 확인할 수 있다고 설명했다. 현재까지 사용되고 있을 가능성이 높다고 판단하지만, 내부 Git에 있는 구현·적용 근거는 외부에서 확인하기 어렵다. 따라서 **재직 당시 개발·내부 배포·사용 경험**, **현재 화면에 대한 사용자 관찰**, **현재 구현과 적용 범위에 대한 추정**을 구분한다. 화면 효과만으로 현재 라이브러리 의존성이나 ‘모든 AI 기능에 사용’이라는 범위를 확정하지 않는다.

**요구사항에 대한 설계 관점:** 사용자는 여러 소비자의 공통·유사 요구를 추상화하여 공통 수준에서 지원하는 방향을 설명했다. 특수 요구에는 애드온·플러그인 같은 확장 지점을 제공하는 방안을 고려하되, 범용성의 경계를 넘는 요구는 실제 조건과 지원 한계를 검토해야 한다고 보았다. 공통 요구의 추상화 방향과 달리, 애드온·플러그인에 관한 조건부 답변은 당시 실제로 구현한 기능으로 기록하지 않는다. 구체적인 요구·대안·결과는 향후 사례 작성 시 회상하여 구분한다.

**책임과 협업에 대한 관점:** 사용자는 독립된 다른 담당 영역의 소유권과 책임을 존중하고, 공동 목표에 타 영역 문제가 생기면 RnR부터 조정하는 접근을 설명했다. 이를 리더십 부족으로 해석하지 않는다. 공동 목표의 의존성·인터페이스·검증 기준을 조율하는 것과 타 담당자의 구현 책임을 대신 맡는 것을 구분한다.

**일반적인 이슈 대응의 맥락:** 사용자 설명에 따르면 삼성에서는 내부 PLM 시스템으로 관련 담당자를 할당하고, 공동 분석과 해결 방안에 따라 담당자를 정해 수정하는 업무를 신입 때부터 경험한다. 일반적인 이슈 대응 절차 자체보다 해당 경험에서 수행한 구체적인 판단과 기여를 설명한다.

### 7.2. 추가할 작업 — WFF 설계 근거 기술 문서 재작성

- 목적: WFF의 명세를 XSD로 설계·구현하던 초기 경험과 공개 코드만으로는 알기 어려운 설계 의도·판단을 공유한다. 그 경험을 통해 XSD 적용의 장점과 한계를 살펴보고 비슷한 문제를 다루는 개발자가 참고할 수 있게 한다. 근거 정리 결과는 이후 포트폴리오 서술 재점검에도 활용한다.
- 위치: 로드맵 1단계의 근거 작성으로 진행 중이다. 블로그 형식을 사용하되 draft로 유지하고, 근거 리뷰 후 공개 표현과 기존 페이지 반영을 결정한다.
- 작성 기반: 사용자 기억, 공개된 당시 버전의 WFF 자료, 공개 가능한 일반 설계 설명. 내부 원본 확보를 선행 조건으로 두지 않는다.
- 산출물: [시리즈 머리말](../src/data/post/wff-xsd-design-rationale-ko.md), [Validation](../src/data/post/wff-xsd-validation-ko.md), [요소·타입 설계](../src/data/post/wff-xsd-element-design-ko.md), [coding convention](../src/data/post/wff-xsd-coding-convention-ko.md), [근거 대조·리뷰 기록](portfolio/wff-xsd-review.md). 사용자 요청에 따라 단일 글을 머리말과 주제별 세 편으로 분리했다. 모두 draft로 유지한다.

내용 구성 제안:

1. 당시 문제·목표·제약과 본인의 담당 범위.
2. 포맷의 철학, 주요 개념의 정의, 구조를 나눈 기준.
3. XSD의 타입·요소·속성·참조 및 구성 관계를 선택한 이유와 대안. 실제 해당했던 항목만 다룬다.
4. 스키마로 표현·검증할 범위와 별도 검증 또는 런타임에 맡길 경계. 당시 판단과 현재 해석을 구분한다.
5. 선택의 장단점과 설명용 예시·도식. 새로 만든 예시는 실제 내부 구현의 복원본으로 표현하지 않는다.
6. 문서화·내부 발표에서 전달하려던 내용과 대상. 대상의 규모·의사결정 영향은 확인된 범위만 기록한다.
7. 개인 기여, 팀·협력사 기여, 기억이 불확실한 부분 및 공개 자료로 확인한 범위.

완료 조건:

- 문서가 내부 원본이 아닌 **회고에 기반해 새로 작성한 설명**임을 밝힌다.
- 당시 설계 이유, 현재의 재해석, 공개 사양의 사실을 구분하고 이후 버전의 특성을 과거 기여에 소급하지 않는다.
- 사용자 검토를 통해 주요 개념·기여 범위·공개 가능한 내용을 정리한다. 기억이 불확실한 부분은 유보한다.
- 외부 독자가 설계 선택의 이유와 한계를 이해할 수 있는 예시 또는 도식을 포함한다.
- 문서 초안 검토 후 Resume·Case Study·Blog 중 반영 위치와 공개 범위를 별도로 결정한다. 초안 작성과 공개는 별도 단계다.

### 7.3. 근거 작성·검토 기준 — 사용자 동의 반영

**근거의 범위:** 공개 코드·문서·제품, 직접 수행한 경험의 구체적인 회고, 설계 이유·대안·제약을 설명하는 기술 문서, 불확실하거나 확인할 수 없는 부분의 기록을 포함한다. 외부 링크나 원본 자료만을 근거로 한정하지 않는다. 자료마다 뒷받침하는 범위를 명시한다. 예를 들어 재작성한 WFF 문서는 설계 사고를 설명하지만 당시 내부 발표 원본이나 모든 의사결정 이력을 대신하지 않는다.

**주장과의 추적 관계:** 경험별 작업 문서에 아래 관계를 짧은 표로 기록한다. 별도 관리 시스템을 만들지는 않는다.

| 기존 주장                           | 관련 근거                  | 근거의 범위·한계              | 검토 후 주장·판단                  |
| ----------------------------------- | -------------------------- | ----------------------------- | ---------------------------------- |
| 현재 페이지의 문구 또는 점검할 주장 | 자료·회고·설계 설명의 위치 | 확인되는 부분과 불확실한 부분 | 유지·수정·축소·유보·재정의 및 이유 |

**작업용 기록과 공개 콘텐츠:** 작업용 문서에서는 불확실한 기억, 폐기한 해석, 기술 세부 사항까지 충분히 검토한다. 이 기록 전체를 공개할 필요는 없다. 근거 검토 후 독자에게 필요한 내용을 선택·요약하고 공개 범위를 결정한다. 근거 작성 중 홍보 문구나 페이지 가독성에 맞추려고 내용을 성급하게 줄이지 않는다.

**선택한 근거 작성 단위의 완료 조건:**

- 무엇을 수행했고 어떤 판단을 내렸는지 설명할 수 있다.
- 개인 기여와 다른 사람·팀의 기여를 구분했다.
- 확실한 내용, 미확인 사항, 근거의 한계를 표시했다.
- 기존 주장의 유지·수정·축소·유보·재정의 여부와 이유를 기록했다.

미확인 사항이 모두 사라져야 완료되는 것은 아니다. 확인할 수 없는 한계를 파악하는 것도 완료 결과로 인정한다.

**콘텐츠 검토와 질문 방식:** 외부 독자가 핵심 전문성, 개인 기여, 역할 범위를 이해하고 면접에서 확인할 논점을 찾을 수 있는지를 살핀다. 사이트의 설명 부족을 실제 경험의 부재로 해석하지 않는다. 질문은 근거 문서 작성에 필요한 구체적인 내용으로 한정하고 기존 답변을 활용한다. WFF·VV의 근거와 설계 내용을 먼저 검토한 뒤 공개 설명의 길이와 형식을 정한다.

**공개 글의 서술 방식:** 역할과 기여는 문제·협업·설계·구현 과정을 통해 자연스럽게 드러낸다. ‘전부 내가 구현’ 같은 공로 강조나 담당·비담당 경계를 반복해서 독자에게 입증하려는 문장을 피한다. 정확한 기여 범위와 근거의 한계는 작업용 기록에서 검토하되, 그 검토 문구를 공개 글에 그대로 옮기지 않는다. 사용자 경험과 기술 선택의 이유를 글의 중심에 둔다.

머리말은 완성도 높은 원고를 목표로 전체 흐름·기술 용어·어감을 통합해 다듬는다. 근거 검토와 후속 글의 미작성 부분을 이유로 머리말을 뼈대 수준에 머물게 하지 않는다. 원고의 완성도와 공개 여부는 구분하며, 공개는 사용자 검토 후 결정한다.

## 8. 세션 간 작업기억 운영 방식

### 당장은 이 문서를 단일 시작점으로 사용

계획, 현재 상태, 합의, 미결정, 다음 행동을 이 파일에서 찾을 수 있게 한다. 세부 자료가 늘어나면 `docs/portfolio/` 아래에 경력 확인표·사례 초안을 분리하고 이 문서에 링크를 추가하는 방식을 제안한다. 빈 문서를 미리 대량 생성하지 않는다. README나 AGENTS의 수정은 이번 범위에 포함하지 않는다.

### 다음 세션 시작 절차

1. 이 문서와 새 사용자 지시를 읽고 최신 합의·다음 작업을 확인한다.
2. `git status --short`, 현재 HEAD, 관련 파일 변경을 확인한다. 이전 세션과 다르면 관찰 내용을 다시 검증한다.
3. 선택한 작업의 목적·대상·완료 조건과 합의 범위를 확인하고 진행한다.
4. 미확인 사실이나 사용자 결정이 필요한 항목만 구체적으로 질문한다. 결정과 무관한 분석은 계속할 수 있다.

### 작업 단위와 상태

- 작업 단위: 경력 항목 1개, 사례 1개, 메인 섹션 1개, 언어 이동 문제 1개 등 독립적으로 검토 가능한 범위.
- 상태: 제안 → 분석 중 → 검토 대기 → 합의됨 → 구현 중 → 검증 중 → 완료. 필요 시 보류와 이유를 기록.
- ‘합의됨’은 사용자 발언 및 날짜를 근거로 기록한다. 제안이나 에이전트 판단을 합의로 승격하지 않는다.
- ‘완료’는 해당 단위의 산출물과 합의된 검증을 마쳤을 때만 사용한다. 구현 완료와 배포 완료를 구분한다.
- 세션 종료 시 변경 파일·결과·검증·남은 항목·다음 행동을 갱신한다. 미실행 검증은 그대로 표시한다.

후속 작업 기록 양식:

```markdown
### 작업 ID — 제목

- 남은 문제 / 다음 행동:
```
